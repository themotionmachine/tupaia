# Map performance regression checks

Run `npm run build && node bench/map.ts` with Node 24 and root Playwright Chromium installed. No live site is contacted. The runner starts a local production preview, blocks external requests, and uses one browser, context and page sequentially. It measures the real app/MCP runtime: generation, .map serialization, .map loading through its completion callback, full redraw of the default preset plus explicitly enabled heightmap and relief layers including render settling, and regrid to 90% of the input density. Requested generated sizes are 10K, 50K and 100K points (packed cell counts differ). A fixed seed, procedural continents template and 1280×720 viewport keep workloads reproducible.

Each size receives one unrecorded warmup and three measured iterations. Every iteration generates a fresh map, saves it, reloads that saved map, redraws, then regrids. Save measures the native project serialization and compression, without filesystem/network throughput. Proposed revisions use prepareMapFile when available and load its binary Blob through the UI completion event; legacy base revisions use their text serialization and load path. The shared-map API remains text. Regrid excludes server undo snapshots. Generate includes render settling. Every operation waits for the optional reliefRenderReady and burgRenderReady promises so PNG generation is included. Redraw includes both dense terrain layers and the default political layers.

Results go to `bench/results/current.json`; override with `BENCH_OUTPUT`, port with `BENCH_PORT`, or samples with `BENCH_SAMPLES` for exploratory runs. Do not run concurrently with another browser suite. JSON records raw samples, medians, CPU, OS, architecture, browser, viewport and seed. Schema 2 includes native binary save/load and burg-render settling; schema 1 historical artifacts are not comparable to this workload.

PR CI runs base and proposed revisions sequentially on the same pinned Ubuntu runner, using the proposed harness for both. This paired baseline prevents local Mac measurements or historical machine differences from becoming CI gates. The comparator refuses mismatched environments, unsupported schemas, and missing, duplicate or invalid measurements on either side. Four pure gate tests verify these rejection paths and the material-regression threshold. A regression fails when its median is both over 25% slower and over 100 ms slower. This tolerance accounts for shared-runner noise; investigate raw samples before changing thresholds. Rerun noisy jobs rather than updating a stored baseline. Artifacts retain both measurements even after failure.

The workflow is also manually runnable. No absolute budgets or fabricated baselines are claimed. A future controlled runner can tighten tolerances after enough repeated measurements.

## Recorded local measurements

The mgm1 artifacts are actual macOS ARM measurements, not CI baselines. `mgm1-stress-base.json` uses an isolated `git archive HEAD` build with the same installed dependencies. `mgm1-stress-head-first.json` records the first working-tree build: its 100K redraw median rose from 1116.8 to 1402.9 ms and the comparator returned exit code 1. That finding led to deferring giant SVG fallback construction and lowering raster resolution to the device pixel ratio. The first-pass artifact is retained as evidence. The original `mgm1-initial.json` uses the pre-existing dist/default layers and is a separate exploratory workload.

A subsequent attempt overlapped an unrelated e2e suite and was stopped. The final schema 2 pair is `mgm1-final-base.json` against `mgm1-final-head-fast-v2.json`, with three measured samples per operation on the same Apple M1 Max, Node v25.6.1 and Chromium 148.0.7778.96. Both revisions use the same schema 2 harness. The default-base baseline and Cloudflare-base proposed build were each previewed with their matching asset base; a preliminary proposed run with a mismatched preview base failed startup and produced no timing artifact.

The strengthened comparator passes all 15 final rows with the unchanged threshold: both a greater-than-25% slowdown and a greater-than-100-ms slowdown are required to fail. This is a completed local paired gate, not an executed CI result. CI is configured to perform the paired comparison independently.

| Requested cells | Generate base → final | Save base → final | Load base → final | Redraw base → final | Regrid base → final |
| --- | --- | --- | --- | --- | --- |
| 10K | 954.5 → 965.3 ms | 37.4 → 86.2 ms | 369.2 → 468.9 ms | 248.0 → 275.0 ms | 847.7 → 689.7 ms |
| 50K | 3291.3 → 2927.5 ms | 89.5 → 153.0 ms | 986.4 → 978.6 ms | 552.1 → 458.3 ms | 2171.2 → 1719.8 ms |
| 100K | 6702.0 → 5926.6 ms | 180.5 → 232.2 ms | 2158.3 → 1950.2 ms | 1164.9 → 790.6 ms | 4115.5 → 2849.9 ms |

The 100K generation, load, redraw and regrid medians improve by 11.6%, 9.6%, 32.1% and 30.8%, respectively. Native saving is slower than baseline at all sizes, but its absolute increases (48.8, 63.5 and 51.7 ms) stay below the gate's material-regression limit. The 10K load is 99.7 ms slower (+27.0%), only 0.3 ms below that absolute limit; this narrow margin is not evidence of robust CI performance. Raw samples are retained, including the final 100K save outlier of 319.2 ms.

Earlier schema 2 failures remain in `mgm1-final-head.json` and `mgm1-final-head-optimized.json`: the optimized attempt passed 12/15 rows and failed saves at every size (37.4 → 165.0, 89.5 → 345.2 and 180.5 → 574.7 ms). Stage profiling identified encoding/compression as the dominant cost. Canonical relief serialization removed duplicate PNG/placement data; native typed snapshots, a fast block codec, optimized overlap decoding and direct typed-array decoding then reduced the save overhead. `mgm1-final-head-fast.json` retained a subsequent 13/15 result, failing 10K load (479.5 ms) and 100K save (294.4 ms), before the final helper/decoder optimization. No thresholds or baseline samples were changed to obtain the final pass.

Host activity snapshots were recorded throughout both completed runs. The final proposed run was dominated by its own Chromium process; observed unrelated activity included `opendirectoryd` around 10–13%, with most other observed processes below 3%. These measurements do not establish an otherwise idle machine, heap/RSS bounds, long-term recovery behavior or a CI pass.
