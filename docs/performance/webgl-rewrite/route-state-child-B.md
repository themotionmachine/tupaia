# Route-state child B: history-dependent GPU prepare cost

Scope: static read of the GPU prepare pipeline for state whose size or cost grows with session history. No tests, builds, browsers, or checks were run. Every number below is a code-reading inference, not a measurement. Marks: VERIFIED-IN-CODE means the file:line was read and the claim follows from it. UNVERIFIED means a hypothesis or an unread path.

Symptom under study: fresh prepare about 1.3 s, after a long session about 90 s, with every phase about 10x slower (cumulative ms: scene 27564, clone 46943, screen 60999, windows 61001, world 90504).

## 2. Top 3 findings by evidence

### Finding 1: `#coas` is the only verified store that grows across a session and sits in the #map clone path

- Evidence: `#coas` is created once at src/index.html:8765, after the #map svg opens at index.html:163 (VERIFIED-IN-CODE; the closing tag is UNVERIFIED). Each distinct emblem id appends an SVG at src/renderers/emblems/renderer.ts:301, and trigger() skips ids already in the DOM (renderer.ts:309). The only clear is src/io/load.ts:138 (`ensureEl("coas").innerHTML = ""`) and public/main.js:1374 (per summary). So the set grows with each new emblem id for the whole session (VERIFIED-IN-CODE for the mechanism).
- Path into prepare: prepareMapClone clones all of #map (src/io/export.ts:257, VERIFIED-IN-CODE), and each compat run serializes the clone (src/gpu/compat.ts:105, VERIFIED-IN-CODE). Clone and compat cost therefore grow with #coas content. This matches "clone" and "world" being slow.
- Limits: whether ids keep changing over a session (new burgs or states) is UNVERIFIED; the cost per COA svg is UNVERIFIED. This explanation does not account for the 10x slowdown in the "scene" phase, which walks the live #viewbox (src/gpu/scene-cache.ts:15 mentions the viewbox identity), unless #coas is inside #viewbox (UNVERIFIED; #coas is in the #map svg, not in #viewbox at index.html:334, as far as read).
- Cheap in-page measure: `document.getElementById("coas").children.length` and `outerHTML.length` at fresh load and after a session; `performance.now()` around `prepareMapClone("gpu", {debug: true})`.

### Finding 2: The uniform 10x across all phases fits a per-yield latency cause better than any single data structure

- Evidence: every phase calls `slicer.tick()` (src/gpu/slice.ts:24-42). Each yield is a MessageChannel hop (slice.ts:7-16). The wall-clock phase marks include the time spent waiting for that hop, and the slice budget does not count it (VERIFIED-IN-CODE). If the macrotask queue grows with session history, each yield waits longer, which inflates all phases in proportion to their number of yields, not their work. That matches the observed near-uniform 10x.
- Candidate sources of queued macrotasks and event-loop load: caravan segment timers and transitions that are not cleared (src/renderers/draw-trade-animation.ts:96, 162-163, liveGroups and the setTimeout chain; VERIFIED-IN-CODE for structure, UNVERIFIED for accumulation), the dialog scan triggered by the documentElement observer (src/gpu/renderer.ts:231-235, 718-727; VERIFIED-IN-CODE; accumulation UNVERIFIED), and the #map mutation observer callbacks (renderer.ts:282-289).
- Limits: this is a hypothesis. The magnitude is not measured. Phase cumulative values also include the actual work. The cause could be GC or heap pressure instead, which would also slow all phases; not checked.
- Cheap in-page measure: a MessageChannel ping round trip (`port1.onmessage`, `port2.postMessage`) timed before and after a session. Count `#tradeAnimation > g` and `document.querySelectorAll(".ui-dialog").length`.

### Finding 3: `device.track()` is O(tracked) per call, so any unreleased resource makes prepare quadratic

- Evidence: `track()` calls `memory()` (src/gpu/device.ts:309-312), and `memory()` walks the whole `tracked` Set (device.ts:289-298). `peak()` also calls `memory()` (device.ts:301-303). `release()` removes from the Set (device.ts:270-273), and `dispose()` releases all (device.ts:325-327). Prepare releases prior resources at src/gpu/prepare.ts:179 (VERIFIED-IN-CODE).
- Consequence: with N tracked resources, creating N more costs O(N²). Growth in N happens only if a resource is tracked and not released. No such leak is confirmed; the `BitmapWindows` release path (bitmap-window.ts) was not read (UNVERIFIED).
- Cheap in-page measure: `renderer.device.memory().count` (device.ts:289-298) at fresh load, after a prepare, and after a long session. A count that rises across prepares with no change in scene size would confirm a leak.
